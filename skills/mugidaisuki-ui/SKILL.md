# mugidaisuki-ui

**先写提示词，再动手做界面。** 用户提出设计需求后，不直接开始写页面：先把需求压缩成一份可执行的设计提示词，再给 2–3 个风格不同、可直接使用的提示词方案，等用户选定一个（或说“你定”）后，才进入 oil-ui 的制作流程。之后每一轮都先更新提示词，再改界面，直到用户接受成品。

本 Skill 是工作流入口；具体设计方法、截图和脚本在 `oil-ui` Skill 里，提示词写法可配合 `prompt-engineering-patterns` Skill。

## 什么时候用

- 新页面、新 App/后台、组件、落地页、品牌页、截图还原、整体改版
- 用户说“帮我设计/优化/重做/看看这个页面”，但还没给出明确的视觉方向
- 用户只给了一个模糊的风格词（高级、干净、日系、科技感）

**不用**：只改文案、调数量、删指定元素、复用现有样式这类小改动；按 oil-ui 的“小改动”路径直接改。

## 流程

### 0. 先接住需求

用一两句话复述：产品是什么、用户是谁、主任务、交付物、已知约束。  
只问会改变方向的问题，最多一次问三个；能推断的自己定，并写明假设。  
回复、提示词和交付说明用用户的语言。

### 1. 写设计提示词 v1

在动手前写一份**设计提示词**，不是代码，也不是页面文案。至少包含：

- 角色/任务：要设计什么，给谁用，最重要的动作
- 内容：真实内容、必须出现的信息、不能编造的内容
- 风格：从品类、品牌、受众和参考里推出的调性
- 视觉：字体方向、色彩、空间、图片/图形、动效
- 约束：设备、品牌资产、技术栈、不能改的东西
- 交付：对比页、HTML、组件、设计说明还是可运行页面
- 验收：用户看到什么算“对”

提示词要具体到能指导构图和选型，不写“高级、干净、现代”这种没有落点的词。提示词写得不够具体，或用户明确要求优化提示词时，加载 `prompt-engineering-patterns` Skill，按它的模板和优化方法处理。

### 2. 给风格提示词方案

给 **2–3 个**真正不同的方向。每个方向写成一张卡片，包含：

- 方向名 + 一句话概念
- 视觉语言：版式骨架、字体、色彩、素材/图形、动效
- **可直接使用的提示词段落**（用户复制给别的模型也能用）
- 适合什么产品、有什么风险

硬规则：

- 任意两个方向至少在版式、字体、色彩、主视觉、动效里有两项不同；不能只换颜色
- 每个方向都从产品本身长出来，不套模型默认模板
- 推荐一个，并说明理由
- 用表格/卡片同屏对比，让用户一句话就能选

结尾只问：选哪个、要不要合并、要不要看实际首屏。**发完结束这一轮，不开始做页面。**

### 3. 等用户选择

- 用户选了一个：方向定下，进入第 4 步
- 用户说“你定/直接做”：选推荐方向，写明假设，继续；仍然先保存提示词
- 用户要合并：先写出合并后的提示词，再确认一次
- 用户要看实际首屏：按 oil-ui 的方向探索做 2–3 个首屏，放进对比页；选定后再做完整页面
- 用户改需求：更新提示词 v2，重新给受影响的方向，不从头再来

### 4. 保存提示词并执行

把选定的提示词写到任务目录，例如：

```text
design/prompts/round-01.md
```

内容包含：用户原话摘要、选定方向、完整提示词、明确不做的部分、验收标准。  
然后加载 `oil-ui` Skill，按它的流程制作；如果当前 oil-ui 提供 `oil_ui_*` 原生工具就用工具，否则按它的「工具」参考用 bash 运行脚本。  
制作时以提示词为准；发现提示词和真实内容冲突，先改提示词并说明，再改页面。

### 5. 一轮一轮打磨

每一轮：

1. 先写这一轮的修改提示词（改什么、为什么、验收点）
2. 再改界面
3. 截真实画面（桌面 + 移动端关键状态）
4. 用一句话说清：这轮改了什么、和提示词的差距、下一轮建议
5. 只问一个聚焦的问题，等用户反馈

把每轮提示词追加到 `design/prompts/round-02.md`、`round-03.md`…，保留决策链。  
用户说“可以了/就这样”才进入交付；不要自己宣布完成。

### 6. 交付

交付说明至少包含：

- 最终提示词（或提示词文件路径）
- 选定方向和理由
- 改了哪些轮、每轮解决什么
- 哪些是真实内容、哪些是模拟/占位
- 截图/证据路径
- 还没做的部分

## 边界

- 不在用户选方向前写完整页面；最多做首屏对比
- 不伪造品牌、客户评价、业务数据
- 不把“示例/示意图/按钮未接入”写进界面
- 不用三个换色方案冒充三个方向
- 用户只要评审时，不改文件
